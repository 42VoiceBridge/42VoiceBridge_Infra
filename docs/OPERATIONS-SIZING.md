# 사양·비용 추정치와 확정 절차

이 문서의 모든 사양과 비용 수치는 **추정치**다. 실제 배포 후 지표로 확정하고 그 결과를 `deploy-step.md`에 기록한다. 2026-10-03 기준 AWS에는 적용하지 않았다.

## 현재 사양은 "초기 시험 사양"이다

| 인스턴스 | 초기 사양(변수) | root | 근거와 한계 |
|---|---|---|---|
| BE | `m5.large` (`be_instance_type`) | 30 GiB | 기존 사양. BE 단독 부하는 측정된 적이 없다 |
| AI | `m5.xlarge` (`ai_instance_type`) | 40 GiB + 데이터 20 GiB | AI팀 실측은 **추론 3건 기준 1.67 GiB**(arm64, 4GB 제한)뿐이고 학습 중 메모리·2~4 vCPU에서의 학습 시간은 없다. 4 vCPU는 CPU 학습 여유를 위한 가정이다 |
| FE | `t3.small` (`fe_instance_type`) | 30 GiB | 정적 파일 서빙(nginx)과 Caddy. 가벼울 것이라는 가정이며 측정되지 않았다. `t3`는 CPU 크레딧 소진 시 성능이 제한된다 |

## 비용 (추정, 검증 전)

- 기존 가이드의 시간당 약 $0.61(EC2 `m5.large` + RDS `db.r5.large` + ElastiCache `cache.m5.large`)에 AI `m5.xlarge`(약 +$0.24/시간 가정)와 FE `t3.small`(약 +$0.03/시간 가정), 인스턴스마다 붙는 공인 IPv4 주소의 시간당 요금(소액)을 더하면 **약 $0.9/시간**이라는 계산이다. 이 단가는 서울 리전의 대략치이며 **AWS 요금 계산기로 확인한 값이 아니다.**
- 이 가정이 맞다면 $100 크레딧은 24시간 상시 가동 기준 4~5일 분량이다. 테스트할 때만 켜고 끝나면 정리한다([데이터 보호 가이드](DATA-PROTECTION.md)의 절차 2).
- EBS(root 3개 + 데이터 20 GiB), 스냅샷, EIP, 데이터 전송, ElastiCache(사용하지 않으면 삭제해야 비용이 멈춘다)도 별도다.
- 확정 방법: 실제 청구 데이터(Cost Explorer 또는 청구서)와 AWS 요금 계산기로 확인하고, 이 문서의 수치를 실측값으로 교체한다.

## 사양 확정 절차

배포 후 아래 순서로 측정하고 결정을 기록한다.

### 1. 측정 도구

- **스냅샷 수집(읽기 전용):** Infra Actions → **SSM deploy (manual)** → `mode=measure`. 세 인스턴스의 `uptime`, `free -m`, `df -h`, `docker ps`, `docker stats --no-stream`, `docker images`를 출력한다. 비밀값은 출력하지 않는다.
- **CloudWatch 기본 지표**(콘솔): EC2 `CPUUtilization`, `NetworkIn/Out`, `CPUCreditBalance`(`t3`), EBS `VolumeReadOps/WriteOps`. **메모리와 디스크 사용률은 CloudWatch 기본 지표에 없다.** 장기 추이가 필요하면 CloudWatch 에이전트를 별도로 도입해야 한다(이번 범위에는 없다).

### 2. 시나리오와 기록 항목

| 시나리오 | 측정 | 기록 |
|---|---|---|
| A. 유휴 | 모든 인스턴스 `measure` | `available` 메모리, 컨테이너별 메모리 |
| B. AI 첫 기동 | AI 배포 로그 | 이미지 pull + 모델 다운로드 + 헬스 200까지의 시간(헬스 대기 600초 안인지) |
| C. 추론 부하 | 요청을 보내는 동안 AI·BE `measure` | AI 컨테이너 메모리 최대치, 응답 시간, AI vCPU 사용률 |
| D. **CPU 학습** | 학습 요청 후 학습이 도는 동안 AI `measure`(여러 번) | 학습 소요 시간, **학습 중 메모리**, 학습 중 추론 응답 시간 |
| E. FE/엣지 | FE `measure`, CloudWatch | 메모리, CPU 크레딧 잔량 |
| F. 디스크 | 각 인스턴스 `df -h` | root·`/data` 사용률 증가 추이 |

### 3. 판단 기준(제안, 실측 후 조정)

| 지표 | 상향·확장 신호 | 하향 신호 |
|---|---|---|
| `available` 메모리 | 부하 중 총 메모리의 20% 미만으로 떨어진다 / 스왑·OOM 종료 흔적 | 모든 시나리오에서 60% 이상 남는다 |
| CPU | 지속적으로 70% 이상 / 학습 시간이 사용자 경험상 허용 범위를 넘는다 | 지속적으로 20% 미만 |
| `t3` CPU 크레딧 | 잔량이 계속 줄어 0에 가깝다 | |
| 디스크 사용률 | 70% 이상이거나 증가 추세가 뚜렷하다 | |
| AI 헬스 대기 | 600초에 가깝거나 넘는다 → 대기 시간·사양 재검토 | |

변경은 변수(`*_instance_type`, `*_root_volume_size_gb`, `data_volume_size_gb`)로 하고, **인스턴스 유형 변경은 정지·재시작을 일으키고 사양에 따라 교체가 될 수 있다.** 교체가 계획되면 apply 워크플로가 `allow_destroy`를 요구하고, apply 후 마지막 성공 배포로 자동 복원된다. AI 인스턴스 변경 전에는 데이터 볼륨의 수동 스냅샷을 만든다.

### 4. 결정 기록

측정 후 `deploy-step.md`의 진행 로그에 다음을 남긴다: 측정 일시, 시나리오, 핵심 수치, 결정(유지/상향/하향)과 근거, 바꾼 변수 값. AI 학습이 BE 응답에 영향을 준다고 확인되면 학습 전용 인스턴스 분리를 새 ADR로 다룬다.

## 확정 전에 하지 않는 것

- 컨테이너 메모리·CPU 상한(`--memory`)은 설정하지 않았다. 실측 후 근거를 가지고 정한다.
- "8 GiB면 충분" 같은 단정은 하지 않는다. 추론 3건 측정만으로는 확정할 수 없다.
